# 校园知识问答助手（RAG）

基于 RAG（检索增强生成）的杭州师范大学校园文档问答服务。学生用口语提问，
系统从校园公开文档里检索依据、生成带**出处引用**的答案；查不到就**明确拒答**，
绝不编造。

这是简历上那个「AI 应用项目」的实现本体。

---

## 一、为什么做这个

**痛点**：新生的高频问题（转专业什么条件、助学贷款怎么办、体质测试在哪测）
答案散在几十份学校文件里，官网站内搜索又不可用，只能靠问学长或辅导员。

**为什么不是"接个 ChatGPT"**：政策类问答一旦编造，代价比答不出更大
（比如错报奖学金金额、错说转专业条件）。所以这个项目的核心不是"调通大模型"，
而是**让答案可核对、让无依据的问题拒答**。下面每个设计点都服务于这个目标。

---

## 二、快速开始

```bash
cd rag
pip install -r requirements.txt

# 1. 构建索引（首次必须）
python -m rag.cli_index

# 2. 提问
python -m rag.cli_ask "转专业需要什么条件"
```

**不需要任何 API Key 就能完整跑通**（原因见「四、两条链路」）。

### 其他常用命令

```bash
python -m rag.cli_ask                              # 交互式问答
python -m rag.cli_search --batch                   # 只看检索结果，不调模型
python -m rag.cli_eval                             # 跑评测，输出 Recall/MRR/拒答率
python -m rag.cli_calibrate                        # 标定拒答阈值
python -m rag.cli_clean                            # 预览语料清洗效果
python -m rag.cli_margin                           # 诊断分档阈值
python -m rag.server                               # 启动 HTTP 服务
python tests/test_rag.py                           # 跑测试（37 项）
```

## 三、实测指标

用 30 道知识库内确有答案的问题 + 12 道库外问题评测（`rag/eval/questions.json`，
逐题人工标注了应命中的文档）：

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| **Recall@5** | **100.0%** | 该召回的文档全部进了 top-5 |
| **MRR** | **0.950** | 正确文档平均排在第 1.05 位 |
| **拒答准确率** | **91.7%** | 12 道库外题，11 道正确拒答 |

复现：`python -m rag.cli_eval`

**唯一的漏网**：问「怎么补办学生证」被误答。原因是命中的《平安保险须知》正文里
含「学生」二字（"新生入学""学生平安保险"），字面重叠导致覆盖率虚高。
本地字面向量下难以消除，换语义 embedding 或补语料才是正解——见「七、已知局限」。

## 四、两条链路：为什么没有 Key 也能跑

| | 向量化 | 生成 |
| --- | --- | --- |
| **默认（离线）** | 字符 n-gram 特征哈希 → 2048 维 | 抽取式：直接给最相关原文 + 出处 |
| **配 Key 后** | 真实 embedding API | 大模型总结式回答，带 [1][2] 引用 |

设计意图：**让整条链路（切分→清洗→检索→生成→评测）在零依赖、零成本、
可复现的前提下先跑通**，配上 Key 自动升级为语义检索，业务代码零改动。

离线向量化的短板是**只做字面匹配**——用户口语提问与文档书面用语不一致时会漏
（"挂科" vs "课程考核不合格"）。但校园制度类文档的用词与提问重合度较高
（"转专业""奖学金""助学贷款"），所以实测召回仍然可用。

### 接入真实大模型（可选）

```bash
# 向量化（可选，配了才有语义泛化能力）
export RAG_EMBED_API_KEY=sk-xxx
export RAG_EMBED_BASE_URL=https://api.deepseek.com/v1
export RAG_EMBED_MODEL=embedding-2

# 生成（配了才有总结式回答）
export RAG_LLM_API_KEY=sk-xxx
export RAG_LLM_BASE_URL=https://api.deepseek.com/v1
export RAG_LLM_MODEL=deepseek-chat
```

Windows PowerShell 用 `$env:RAG_LLM_API_KEY="sk-xxx"`。

> ⚠ **换了向量化方式后必须重新标定拒答阈值**：`python -m rag.cli_calibrate`。
> 不同向量的余弦分布尺度完全不同，沿用旧阈值会大面积误判。

## 五、四个关键设计（面试会问的部分）

### 1. 按条款边界切分，而不是按固定长度硬切

校园制度文档有天然结构（「第X条」「一、」「（一）」）。一个条款通常就是一个
完整语义单元，按固定长度硬切会把条款切碎，导致检索到半句话。

实现见 `chunker.py:split_text`——先按条款标记聚合成"条款单元"，条款内部再按
句子退让，最后才硬切；并用 chunk_overlap=80 避免答案正好跨在边界上被截断。

### 2. 跨文档重复行检测来清模板噪声

采集下来的网页正文混着导航噪声。实测「课程思政教学研究中心」「创新创业学分」
这类栏目名出现在 11 个页面上——它们会被算进相似度，严重污染检索。

不需要事先知道模板长什么样：**一行若出现在 ≥25% 的文档里，它就是站点模板**。
这个办法对任何 CMS 站点都适用。配合规则清洗（面包屑、来源行、页脚），
实测删掉 9% 的字符，且标题抢救准确率大幅提升（原本全是"杭州师范大学教务处"，
现在能正确识别出《本科生转专业实施办法》这类真标题）。

见 `cleaner.py`。

### 3. 拒答用两道闸，且第二道只作用于低分带

这是本项目调参最花时间的地方，过程都留在代码注释里：

**第一道：相似度阈值 0.11**。不是拍脑袋定的——用 10 道库内题 + 10 道库外题
对比分数分布，本地 n-gram 下两组分得很开（库内 min=0.1188 / 库外 max=0.1042），
阈值正好落在空隙里。见 `cli_calibrate`。

**第二道：关键词覆盖率，只作用于 score < 0.25 的情况**。

为什么不只用相似度：问「怎么补办学生证」会命中《平安保险须知》，
分数 0.1191 刚好越线。

为什么不一刀切用覆盖率：高分段存在覆盖率偏低却正确的结果
（「转专业每学期可以填几个志愿」覆盖率仅 0.30），一刀切会把
Recall@5 从 100% 拉到 90%。

所以分档：`score >= 0.25` 直接采信；`score < 0.25` 再要求覆盖率达标。
调完三个指标同时达标。

### 4. 覆盖率用字符二元组，不用分词

最初用"连续汉字串"当词，结果「什么情况下不能转专业」整串被当成**一个词**，
它在文档里当然不存在，覆盖率算成 0——指标直接失效，误杀 3 道题。

改用二元组：不需要分词器（`jieba` 等会引入依赖），且对
「转专业 → 转专业实施办法」这类包含关系天然友好。这个 bug 有回归测试保护。

## 七、已知局限（如实记录）

1. **「怎么补办学生证」被误答**（拒答准确率 91.7% 而非 100%）。
   命中文档正文含「学生」二字导致覆盖率虚高。本地字面向量难以解决。

2. **同义改写会漏**。离线向量只做字面匹配，问「挂科了怎么办」而文档写
   「课程考核不合格」时检索不到。需要 API embedding 或加一层查询改写。

3. **语料覆盖不全**。目前只有学校官网上能公开抓到的 30 份文档，
   **缺学生手册、培养方案、图书馆规则、宿舍管理规定**等核心文件——
   教务处「规章制度」栏目翻到底也只有 8 篇，核心制度很可能没公开挂出，
   图书馆站点返回首页仅 2.9KB、零链接，无法采集。
   这直接导致「图书馆借书能借几本」「宿舍可以住到什么时候」这类问题
   只能拒答。**补语料比调参的收益大得多。**

4. **评测集规模偏小**（42 题）。指标数量级可信，但小幅波动不必当真。

5. **单查询单轮检索**。没有做 query 改写与多轮指代消解——
   「那重修呢？」这类追问无法正确解析。

### 后续可做的改进（按性价比排序）

1. 补齐核心语料（学生手册、培养方案）——收益最大
2. 接 API embedding 换语义检索，然后重新标定阈值
3. 加查询改写层（用大模型把口语问题改写成检索友好查询）
4. 加多轮对话的指代消解
5. 扩充评测集到 100+ 题

## 八、HTTP 接口

```bash
python -m rag.server
# 服务：http://127.0.0.1:8000
# 交互文档：http://127.0.0.1:8000/docs
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查 |
| GET | `/info` | 索引与链路信息 |
| POST | `/ask` | 问答（检索 + 生成 + 引用） |
| POST | `/retrieve` | 只检索不生成 |
| POST | `/rebuild` | 重建索引 |

示例：

```bash
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"转专业需要什么条件","top_k":3}'
```

返回：

```json
{
  "question": "转专业需要什么条件",
  "grounded": true,
  "answer": "……",
  "citations": [
    {"index": 1, "doc_id": "doc-001", "title": "普通高等学校学生管理规定",
     "url": "https://jwc.hznu.edu.cn/c/2017-09-12/1857835.shtml",
     "score": 0.1188}
  ],
  "source": "extractive",
  "elapsed_ms": 2
}
```

`source` 取值：`llm`（大模型生成）/ `extractive`（离线抽取式）/ `refused`（拒答）。

## 十、这份项目能写进简历的点

1. **完整的 RAG 工程链路**：采集 → 清洗 → 切分 → 向量化 → 检索 → 生成 → 评测，
   每一环都有可复现的实现与可量化的产出
2. **检索质量可测量**：自建 42 题评测集（人工逐题标注应命中文档），
   Recall@5 100% / MRR 0.950
3. **拒答设计有依据**：阈值由分布标定而非拍脑袋；覆盖率闸门分档作用于低分带，
   有"一刀切导致 Recall 从 100% 掉到 90%"的实测对比
4. **噪声清洗用了通用方法**：跨文档重复行检测，不依赖对某个站点的事先了解
5. **降级链路完整**：无 Key 也能全链路运行，有 Key 自动升级，服务不中断
6. **两个历史 bug 有回归测试保护**：整串汉字被当单词、夹文字的分隔线漏清洗
